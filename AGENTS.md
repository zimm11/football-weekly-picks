# Football Weekly Picks

The app is called **POW Pick'em** in everything players see, and lives at `www.pow-pickem.com`. "Football Weekly Picks" is the repository and service name only.

An NFL pick'em league: each week players pick every game against the spread, mark one Pick of the Week (POW),
and guess the Monday night total as a tiebreaker. A league's admins (commissioners, to players) set up and close each week. See "Domain rules".

pnpm monorepo: an Expo (React Native) app for iPhone and the web + Hono API (TypeScript) + Supabase (managed Auth

- Postgres). Deployed by GitHub Actions as one Cloudflare Worker: Static Assets serve the client-side SPA (the Expo
  web build) from the edge, and `/api/*` runs the
  Hono API in the Workers runtime, reaching Postgres through Hyperdrive. One origin, no proxy, no cold starts.
  Local development and tests run the same API on Node. Code the API runs must work in both: no native addons,
  no files read from disk at runtime, and nothing shared between requests except settled values (see
  "Runtime").

## Layout

- `apps/api` — Hono API. `src/accounts.ts` is account deletion. `src/app.ts` builds the app (`createApp` takes deps, so tests inject fakes) and has the health, config and profile routes; the rest live in `src/leagues.ts` (leagues, members, invites, standings), `src/weeks.ts` (week setup, games, picks, results, recap, insights), `src/messages.ts` (the message board) and `src/operator.ts` (feedback, and the operator dashboard for `OPERATOR_USER_IDS`), `src/moderation.ts` (who may post, reports, blocks, removals, strikes, mutes, suspensions, appeals and the review queues). League types: each type's own routes are a module mounted in `app.ts` (`src/playoff.ts`, `src/squares.ts`, `src/survivor.ts`, each `<type>Routes(deps, services)` plus `<type>Hooks`), `src/typeHooks.ts` dispatches shared events to them (`memberRemoved`, inside the membership change's transaction; `startSeason`, see "Start season"; weekly's hooks are `src/weekly.ts`), and `src/weekOps.ts` holds the week chores every type and automation share (`importSlate`, `openProblem`/`openWeek`, `writeFinals`, `providerWeeks` (the results throttle), `fillFinishedGames`, `finalizeProblem`/`finalizeWeek`, `markRecapSeen`, `reopenWeek`), each taking a database handle or a transaction. `src/automation/` runs leagues that run themselves: `index.ts` (`advanceLeagues`, the cron's entry; `advanceLeague`; `AUTOMATION`, one `LeagueTypeAutomation` per type with `due(ctx, limit)` and `advance(ctx, league)`), `types.ts`, and one handler file per type. `src/services.ts` (`createServices`) holds what route modules share per app instance: the provider's weeks behind the results throttle and `advanceLeagueOnRead` (a one-minute per-league throttle, settled values only), which league, week, survivor and board reads call first. `src/leagueEvents.ts` queues the `league_event` notification kind (`queueLeagueEvent`, `deliverLeagueEventsSoon`). `src/auth.ts` verifies Supabase access tokens (`requireAuth`); `src/context.ts` has the access checks and the shared `param`/`query`/`body` validators; `src/nfl.ts` is the schedule/odds/results provider (ESPN's public scoreboard feed). `src/insights.ts` is the provider behind each game's matchup sheet: team form, injuries, news and each team's chance to win (the Matchup Predictor) from ESPN's game summary, cached in memory. Email: `src/email.ts` (mailers: Cloudflare's `send_email` binding in production, the local test inbox in development; signed unsubscribe tokens), `src/templates.ts` (notification emails), `src/outbox.ts` (queueing, sending and retrying through the `email_outbox` table; pick reminders; `runEmailJobs`), `src/reminderTargets.ts` (who is due a pick reminder, and the send-time recheck, shared by email and push; `REMINDERS` dispatches by league type to a `ReminderHandler`, weekly's in the file and the others in `src/reminders/<type>.ts`), `src/unsubscribe.ts` (one-click `POST /unsubscribe`). Push: `src/push.ts` (device subscription routes), `src/pushQueue.ts` (queueing and sending through `push_deliveries`), `src/pushSender.ts` and `src/webPush.ts` (Web Push on WebCrypto and fetch, no `web-push` package, so the Worker can send). `src/screening.ts` (content screening with Cloudflare's Clef models on the Worker's `AI` binding; the policy in plain words), `src/moderationJobs.ts` (rechecking unchecked posts, clearing removed text, the operator's digest). `src/jobs.ts` (`runScheduledJobs`, which the Cron Trigger calls: `runModerationJobs` and `advanceLeagues`, then `runEmailJobs` and `runPushJobs`). `scripts/moderation-eval.ts` (`pnpm moderation:eval`) checks the thresholds against labeled messages. `src/env.ts` validates the environment, `src/logging.ts` is the safe logger, `src/clock.ts` the local clock override, `src/devHarness.ts` the local E2E harness (a scripted feed and a movable clock for the Worker, `DEV_HARNESS`), `src/index.ts` the Node entrypoint (local dev, tests), and `src/worker.ts` the Cloudflare Worker entrypoint (production). `wrangler.jsonc` configures the Worker; `worker-configuration.d.ts` is generated by `pnpm --filter @picks/api cf-typegen` (rerun after changing bindings).
- `apps/mobile` — Expo Router + React Native client for iPhone and the website (react-native-web); there is no other web client. Uses the same API and `@picks/shared`. Routes live in `app/` (thin files that render a screen; `app/_layout.tsx` holds the providers, fonts, header and `Splash`), screen implementations in `src/screens/` (they fetch, with `useLeagueLoad` in `leagueUi.tsx` or `useResource` in `src/lib/hooks.ts`), shared components and the theme in `src/components/`, and session/API/deep-link/push/storage adapters and pure helpers in `src/lib/` (`api.ts` makes API requests and holds the Supabase client; `auth.tsx` the session; `clock.ts` the clock; `notify.tsx` the banner; `unsaved.ts` the unsaved-work guard; `pickDraft.ts`, `weekPresentation.ts`, `leagueLogic.ts`, `seasonSelection.ts`, `newLeague.ts` and friends are pure and unit-tested). League types: `src/screens/LeagueScreen.tsx` is the shared shell (header, tabs from the registry, Messages, the League tab); `src/screens/leagueTypeScreens.tsx` maps each type to its tab screens, League-tab admin tools and recap (`LEAGUE_TYPE_SCREENS`), and each type's screens live in its own folder exporting its entry from `index.tsx`: `src/screens/weekly/` (Picks, Results, Standings, Set up a week, the recap), `playoff/`, `squares/` (with `BoardScreen.tsx` for `/boards/[id]` and `/boards/[id]/manage`) and `survivor/`. Web-only variants live in `*.web.ts(x)` files beside the native ones (Metro picks one per platform): browser push (`notifications.web.ts`, `DeviceNotifications.web.tsx`, `NotificationsPrompt.web.tsx`), the browser history guard (`browserGuard.web.ts`), `<select>` (`WebSelect.web.tsx`), storage, and bundle trims (`GestureRoot.web.tsx`, `urlPolyfill.web.ts`, `zodLocales.web.js` with `metro.config.cjs`). `pnpm --filter @picks/mobile build:web` (part of `pnpm build`) exports the web build to `dist-web`, the Worker's static assets: one bundle (`asyncRoutes.web: false` in `app.json`, so an open tab survives a deploy). `public/` holds `_headers`, `manifest.json` and the icons, `push-sw.js` and the page template `index.html` with `boot.css`, copied to the build's root. Run `pnpm mobile:check` and `pnpm mobile:export` after app changes. See `apps/mobile/README.md` for device setup and release prerequisites, and `docs/web-cutover.md` for how it replaced the old Vite web app.
- `e2e/` — Playwright end-to-end tests and config.
- `scripts/` — `ports.mjs` (per-worktree ports), `ci-ports.mjs` (a free port group for CI), `supabase.mjs` (CLI wrapper), `supabase-env.mjs` (writes `.env`), `check-db-url.mjs` (checks a connection string without printing the password: `pbpaste | node scripts/check-db-url.mjs`), `icons.mjs` (draws the app icons), `worker-dev.mjs` (`pnpm worker:dev`), `check-live.mjs` (the deploy's live health check, also run every 15 minutes by `uptime.yml`), `vapid-keys.mjs` (a new Web Push key pair), `mobile-dev.mjs` (`pnpm mobile`, and `pnpm dev`), `contract-issue.mjs` (the feed contract alert's issue text). The `*.test.mjs` files beside them run under Node's test runner; `headers.test.mjs` keeps `_headers`' security headers and CSP in place.
- `packages/db` — Drizzle schema (`src/schema.ts`, the **source of truth** for the DB), the `createDb` client (Node) and `createHyperdriveDb` (one connection per Worker request), and the TLS policy (`src/connection.ts`).
- `packages/shared` — Zod schemas and types shared by the API and the app. `src/rules.ts` is the rules engine (point values, locks, scoring, tiebreakers) as pure functions; change league rules there. `src/awards.ts` derives the weekly awards, `src/stats.ts` the season and week analytics shown on Standings and Results, and `src/seasons.ts` holds season defaults, guided week suggestions, display phases, and actionable pick counts. `src/reminders.ts` decides when a pick reminder is due. `src/time.ts` has the time-zone helpers (`canonicalTimeZone`), `src/teams.ts` the NFL teams, `src/leagueTypes.ts` the league type registry (below), `src/playoff.ts`, `src/squares.ts` and `src/survivor.ts` each type's rules and settings schema, and `src/insights.ts`, `src/push.ts`, `src/messages.ts` and `src/operator.ts` the schemas for those features. `src/index.ts` also holds the league size limits.

Update the seed when a schema change would break it.

## Commands (run from repo root)

Server logs go to `apps/mobile/.expo/logs/`. `pnpm mobile:prod` runs Metro against production.
- `pnpm worker:dev` — the production build as Cloudflare runs it (Expo web build + API in the Workers runtime via `wrangler dev`) against local Supabase, on `PORT + 1000`. E2E runs against it. `EXPO_WEB_OUT=<dir>` builds into another folder, so parallel runs don't collide.

## Domain rules

- **League types:** every league has a type (`leagues.type`), fixed when it is created: `weekly` (Weekly pick'em, everything below; the default, and every league from before types), `playoff`, `squares` or `survivor`. The registry `packages/shared/src/leagueTypes.ts` (`LEAGUE_TYPE_INFO`) says what each owns: name, description, icon, settings schema (stored per season in `seasons.settings`, parsed with it on every write and read), the weeks it covers, whether a new league gets its first season when created (`seasonOnCreate`), how it can be run (`management`), its reveal point and its tabs; the API, the app and the cron read it. Membership, admins, invites, the message board, email and push, Settings and the size limits are shared. Every type-specific route checks the type first (`requireLeagueType`, `requireBoard` in `context.ts`) and answers 404 for another type; the week, game and pick routes in `weeks.ts` serve weekly and playoff leagues (the matchup sheet survivor too), and week creation there still stops at 18. A weekly league is run `manual` (Hands-on, the admins run each week; existing leagues and creates without `management`) or `auto` (Automatic: the feed does the chores); the other types are always `auto`, and a CHECK keeps manual to weekly. Every type, and Automatic for weekly, is open to every player. **New league** shows the four type cards (weekly first and preselected), then **How do you want to run it?** for weekly (Automatic preselected, or Hands-on), the type's settings, and **Start with members from** (default Nobody). An admin switches Automatic/Hands-on in League → League settings at any time. Your leagues shows each league's type as a badge. How to play (`app/how-to-play.tsx`) has one tab per type (`?section=<type>` selects one, and the tab sets it back, so links and Back keep the tab; each type's text lives in its own `HowToPlay<Type>.tsx`), with what every league shares (accounts, invites, admins, messages, reminders) under the tabs. The signed-out home page pitches Weekly pick'em and lists the other games in a quieter **More ways to play** strip that links to their tabs. Under the type cards, **How <type> works** opens How to play at that type's section (`/how-to-play?section=<type>`; `app/how-to-play.tsx` scrolls to the section registered under that key, weekly's being the pick rules).
- **Squares:** a squares league holds boards (`square_boards`), each a 10 by 10 grid on one NFL game: the season's Super Bowl by default once the feed lists it, any feed game (`year`, `week`, `external_id` stored), or teams and a kickoff typed by hand (league time). The rules are pure functions in `packages/shared/src/squares.ts`; the routes are `apps/api/src/squares.ts`, every one behind `requireBoard` or `requireLeagueType("squares")`. Rows are the away team's side, columns the home team's. Players claim squares up to `max_per_player` (default 10, 1–100; raised before the lock, never lowered) and release their own until the lock; an admin can claim under a typed guest name (outside every limit; guests can win but are never notified; the name is screened like a display name, and a suspended admin can't add one) and release any square before the lock. Every claim, release, lock and score write takes the board row lock first. The board is locked once drawn, or from kickoff even before the draw has run. **Lock and draw** (admin, with a confirm naming the open squares) or automation at kickoff draws two unbiased Fisher–Yates orders of 0–9 (`drawDigits`, the `random` dep: `crypto.getRandomValues` by default) inside the lock's transaction, guarded by `drawn_at is null`, so it happens once. Each period (q1, half, q3, final with overtime) is won by the square matching the last digits of the cumulative scores (`squareWinners`); an empty square that hits means no winner. Automation (`automation/squares.ts`) moves an undrawn feed board to the feed's kickoff when the game is rescheduled (on a read, and before a draw), then fills `square_scores` from `ProviderGame.periodScores` once settled, never over an admin's (`by_admin`), for a day after kickoff. An admin can delete a board at any time (`DELETE /boards/:id`, behind the board row lock; claims, scores and queued pushes cascade). Phases (Open, Locked, Underway, Final) and winners are derived on read; while the game is on, `GET /boards/:id` adds the feed's live score (`ProviderGame.liveScore`) and the square that would win now. League events: "The numbers are drawn" by email and push, each quarter's result by push only, both with `boardId`, never naming a square or a team. The reminder (`reminders/squares.ts`) goes to members holding no square on a board still open, at 7pm league time the evening before kickoff, and is rechecked at send time. `squaresHooks.memberRemoved` gives back a leaving member's squares on boards not yet locked. The app: the Board tab shows the board chosen in the header's board selector (`HeaderSelector` in `LEAGUE_TYPE_SCREENS`; the season selector is off), `/boards/:id` the same board, `/boards/:id/manage` the admin's game, limit, guest squares, Lock and draw, score corrections and Delete board, and League → New board creates one (`src/screens/squares/`). Claiming is optimistic and rolls back with `notifyError`; the first claim offers the home screen. Seed: `supabase/seeds/squares.sql`.
- **Copying members:** `copyMembersFrom` on `POST /leagues` names a league the creator is an admin of; its current members join the new league as members (not admins) in the create transaction, under the same caps and locks as a join (each player's league-count lock taken in one sorted order). Anyone at `MAX_LEAGUES_PER_USER`, or past a full league, is skipped and named in the response (`skipped`). Each added player gets one league event and can leave from the League tab.
- **Week line:** weeks 1–18 are the regular season, 19 Wild Card, 20 Divisional, 21 Conference, 22 Super Bowl (`weekLabel`, `POSTSEASON_ROUNDS` in `seasons.ts`; a CHECK holds `weeks.number` to 1–22). The provider maps 19–21 onto ESPN's postseason weeks 1–3 and finds the Super Bowl's week in the feed's calendar (5 after a Pro Bowl week; the 2026 season lists it as 4). It drops "TBD at TBD" games until both teams are known, and reports each game's status, current period and cumulative score per settled quarter (`periodScores`: q1, half, q3, final with overtime).
- **Structure:** league → seasons (by year) → weeks (1–18 for weekly pick'em) → games → picks. A league keeps its members across seasons. Whoever creates a league is its first admin; others join through its invite link (`/join/<code>`), which an admin can replace so old links stop working.
- **Admins (commissioners):** players call a league's admins **commissioners**, and everything they read says so: the app, How to play, the Terms of use and Privacy policy, API error messages, emails and push ("Make commissioner", "Revoke commissioner", the **Commissioner** pill, "For commissioners"). Code, the API's fields and the database keep `admin` (`league_members.role = 'admin'`, `requireAdmin`, `AdminTools`, `byAdmin`); don't rename them, since stored rows and installed apps depend on them. These docs say "admin". A league can have several, all equal. Any admin can make a member an admin, revoke another admin (or themselves), and remove members, including the creator. A league always keeps at least one admin. "The admin" below means any of them.
- **Limits:** at most 100 active members in a league and 25 active leagues per player (`MAX_LEAGUE_MEMBERS`, `MAX_LEAGUES_PER_USER` in `packages/shared`). Creates and joins check them under a lock; rejoining a league you are already in counts against neither.
- **Home-screen help:** browser users find it in Settings (the **Home screen app** card, **Show me how**; left out in an iPhone tab, where the notifications card shows the steps); it opens a bottom sheet with the steps for their platform (iOS or Android; both elsewhere) without leaving the page. On a phone, the first successful pick save in a browser opens the same sheet once, with **Not now** (`pow:home-screen-offered` in localStorage; no storage means no offer). Computers never get the automatic offer. Hide all of it in standalone mode (including iOS). The logic is in `apps/mobile/src/components/HomeScreenInstall.tsx` and `src/lib/homeScreen.ts`.
- **Profile pictures:** Settings → Profile picture offers 100 bundled logos across five collections. The optional `profiles.avatar_id` selects the same picture across leagues and devices. A null selection shows initials. Account deletion clears the selection.
- **Accounts:** email and password through Supabase Auth, then a display name (required before anything else; the API refuses to create or join a league, or post, without one). "Forgot password?" emails a link that signs the player in on `/reset-password`; the account menu reaches the same screen as "Change password". `/`, `/login`, `/how-to-play`, `/terms` and `/privacy` work signed out. Settings → **Delete account** (`DELETE /me` with the password, `src/accounts.ts`) deletes at once: personal data is cleared in one transaction (devices, queued email, blocks, reactions, reads, picks in weeks that aren't final (survivor picks too), squares on boards that haven't locked, message text; their threads keep others' replies under `DELETED_THREAD_TITLE`; feedback they sent stays without its sender), they leave every league (a league they were the only member of is deleted), the profile becomes `DELETED_PLAYER_NAME` with `deleted_at`, and then Supabase Auth soft-deletes the user (the `auth.users` row stays, email scrambled, so picks from final weeks keep their foreign keys and nobody's results change). Never hard-delete an `auth.users` row: it cascades through every table. `refuseDeletedAccounts` wraps the token check at both entrypoints, so a deleted account's unexpired tokens are refused; tests that cover deletion wrap their verifier the same way. A league's only admin must hand over admin first. Needs `SUPABASE_SECRET_KEY`.
- **Week lifecycle:** `draft` (admin only: import games and spreads from the provider, then add/remove games, edit spreads and point values; a kickoff typed in by hand is in the league's time zone, and a game whose kickoff moves, by re-import or edit, takes the new slot's default points unless the admin had set them by hand) → `open` (players pick; spreads are fixed unless the admin edits them) → `final` (scored; everyone's picks revealed). Results arrive three ways: automatically (below), the admin's "Auto-fill results" (which replaces typed scores), or typed in by hand. Then the admin closes the week; a closed week can be reopened to correct it.
- **Live results:** `GET /weeks/:id` on an open week fills in the provider's final scores for games that came from it, have been under way at least 2.5 hours, and have no result. It never overwrites a score already entered and never touches spreads. The provider is asked at most once a minute per season week (`RESULTS_REFRESH_MS` in `apps/api/src/weeks.ts`), shared across leagues, and a failure is remembered for the same minute. It runs on read, not on a timer, so nothing runs while nobody is looking. While a game has kicked off without a result, the pick sheet refetches the week every minute and when the tab becomes visible again. It marks each settled pick Won (with points), Lost or Push, and `WeekSoFar` totals the player's own points, record and POW (`scoreSoFar` in `rules.ts`). That is the player's own data only, so the privacy rule holds.
- **Picks are private until the type's reveal point** (`LEAGUE_TYPE_INFO[type].reveal`): for weekly and playoff, no endpoint returns another player's picks, points or standings contribution for a week that isn't `final`; a survivor pick shows from its team's kickoff (before that the API says nothing about it, not even that one exists); a squares board is public.
- **Points:** Thursday and Monday 3; Sunday night, Tuesday, Wednesday, Friday, Saturday 2; other Sunday games 1; Thanksgiving and Christmas Day 4. A winning POW adds 5. A push scores nothing and is neither a win nor a loss. Spreads are stored as the home team's line.
- **Locks:** each game locks at its kickoff. Until then its pick can be added or changed, and the POW can be put on it, moved off it, or removed. Once the game holding a player's POW has kicked off, the POW can't be moved or removed. A game with a result entered is locked whatever the clock says. The tiebreaker guess can be entered or changed until the tiebreaker game locks. There is no automatic POW: a player who doesn't choose one has none that week. On the pick sheet, an unsaved change on a game that locks (or was removed) is undone before saving, and the save bar says which change didn't make it. The league's time zone (stored as a canonical IANA Area/City name, or UTC) only decides how game days and times are shown. The tiebreaker game is the admin's explicit choice if they made one, otherwise the last Monday game (else the last game), worked out from the slate on every read.
- **Screens:** a league's tabs come from its type (`LEAGUE_TYPE_INFO[type].tabs`; weekly and playoff: Picks, Results, Standings, Messages, League; survivor: Pick, Standings, Messages, League; squares: Board, Messages, League); the first is `/leagues/:id`, and a tab path the type lacks is the not-found screen. For weekly pick'em, five tabs (a bar along the bottom on phones, a row under the league name on wider screens): `/leagues/:id` is **Picks** (the pick sheet for the current open week: prioritize missing picks that can still be submitted, then editable picks, then any available games, else the latest open week; keep the displayed sheet stable during background refreshes), `/leagues/:id/results` lists closed weeks, `/leagues/:id/standings` is the season table, `/leagues/:id/messages` is the league-wide message board (threads, replies, and per-player unread indicators), and `/leagues/:id/league` has members and the admin's tools (set up a week, invite link, settings). `/weeks/:id` is one week as every player sees it: the pick sheet while open, results once final; saving picks stays on the sheet. `/weeks/:id/manage` is admin-only week management (games, spreads, results, open/close); after opening or finalizing a week in a Hands-on league it offers to post a message-board thread announcing it (a league that runs itself announces with league events instead). Keep picking and managing on separate screens. `/boards/:id` is one squares board and `/boards/:id/manage` its admin screen (see "Squares"). Outside leagues: `/join/<code>` joins through an invite, `/feedback` sends feedback (at most `FEEDBACK_DAILY_LIMIT`, 5, a day), `/operator` is the operator dashboard (feedback inbox and app-wide counts; a 404 for anyone not in `OPERATOR_USER_IDS`), `/terms` is the Terms of use and `/privacy` the Privacy policy (both work signed out), `/account` is **Settings** (notifications by email and on this device, the home-screen app, email address, blocked players, support contact, Terms and Privacy policy, and a link to change password; `/notifications` shows it too, for old links), `/reset-password` is where a password-reset email lands and where the account menu's **Change password** goes, and `/unsubscribe?token=` asks before turning an email off and works signed out (mail scanners open links, so nothing changes on a GET).
- **Announcements and quotes:** only league admins can pin, unpin or permanently delete threads. Deletion uses the thread’s ⋯ menu and a confirmation, removes all replies, reactions, read markers and queued notifications, then returns to the message board. Pinned announcements appear first on the board without changing unread status. The board loads 30 threads at a time (pinned ones always on the first page) with **Load older threads**. A player can start at most five threads a day in one league (`THREAD_DAILY_LIMIT`, since each one emails and notifies everybody; two in an account's first 24 hours), and post at most ten replies a minute (`REPLY_MINUTE_LIMIT`; twenty a day for a new account), never the same reply twice in a row. Members can quote any message in the same thread when replying; the composer previews the quote and lets them remove it without losing their draft. Posted quotes attribute the original author and link back to the original message.
- **Content moderation** (App Store guideline 1.2; README, "Content moderation"): posting, replying and reacting need agreed Terms of use (`profiles.terms_accepted_at`: the first name step's checkbox, which also confirms the player is `MINIMUM_AGE` (18) or older, else a one-time sheet; `/terms` works signed out). Every thread, reply, display name, league name and squares guest name is screened before it is saved (`screen` in `src/moderation.ts`; a guest name as a `display_name`, before the board's transaction): two outcomes only: block refuses it with `MODERATION_MESSAGES`, allow saves it, and no answer saves it `unchecked` for the cron's recheck (which hides and flags it in `content_reports` if it should have been blocked). Borderline content is left to reports; don't add a review verdict. Without a screener (`MODERATION_MODE=off`, Node, tests) content saves `skipped`. Never write offensive words into the repo: the policy is plain words in `screening.ts`, tests use the placeholder `forbiddenword`, and labeled abusive examples stay outside the repo (`MODERATION_EVAL_FILE`). Players report messages, names and the league name (`POST /reports`, 20 a day); two reporters or a threat report hide a message (`hidden_at`), and the larger model can remove it. League admins review their league's reports except those about admins, league names and appeals, which only the operator sees (`GET /operator/reports`). Removal is soft (`removed_at`; the API replaces the body with `REMOVED_TEXT`/`HIDDEN_TEXT` for readers who may not see it, so old clients show the placeholder); removing a thread's first message removes the thread; text is cleared after 30 days. Removals in 30 days are strikes: the second mutes the author app-wide for 24 hours, the third for 7 days. Admins mute members per league (`league_members.muted_until`); the operator mutes and suspends app-wide. **A mute or suspension never touches picking**: don't add moderation checks to pick, week or standings routes. Blocks (`user_blocks`) are one-way and app-wide: the blocker doesn't see the blocked player's threads (board and unread count), sees their replies collapsed (`state: "blocked"`), doesn't count their reactions, and isn't emailed or notified about their threads (checked when queued and when sent). Every action is logged in `moderation_actions`. Operators get an immediate email for threat reports and a daily digest (`email_outbox` kind `moderation`).
- **Message reactions:** active members can add or remove 👍, 😂, 🔥, 🎉, 😮, 🙏 and 🏈 on any message or reply, once per emoji per player. A message shows only the emoji someone has used, with counts and your own selections; the smiley button ("Add reaction") opens the full set. Reactions do not bump threads or mark them unread.
- **Season and week UI:** one season selector applies across the season-based league tabs and is remembered per league in browser session storage. It is a pill on the header's "All leagues" row (`LeagueHeader` in `LeagueChrome.tsx`), with the league's name on its own line below, so a long selector ("2026 playoffs", a squares board's game) never squeezes the name; squares' board selector is the same pill. New seasons are staged explicitly and created with their first week. Future drafts do not displace the default published season. The admin chooses from weeks 1–18 with existing states shown; existing weeks open management instead of creating duplicates. Display phases are derived from kickoffs and scores (Draft → Accepting picks → Games underway → Awaiting finalization → Final); the database still stores only draft/open/final. Only an admin finalizes a week, using **Finalize week**.
- **Membership and history:** removing a player, or a player leaving (League tab → Leave league; the only admin can't until someone else is one), marks the membership (`removed_at`) instead of deleting it. They lose access and can rejoin through an invite link. Each closed week is scored for the people who were in the league when it was played: a player removed after the week's last kickoff stays in it, and one who joined after it isn't added. Finalizing records that list in `week_participants` (everyone in the league at the last kickoff, plus anyone who picked); leaving or rejoining later never changes it, and finalizing again after a reopen only adds players. Weeks finalized before the table existed have no rows and are worked out from membership dates. Don't score past weeks from the current member list.
- **Pick submissions** run in one transaction that locks the week row and takes a per-player advisory lock, so the lock rules can't be raced. Keep reads, validation and writes inside it.
- **Weekly winner:** most points, then most games won, then closest guess at the tiebreaker game's total (on equal distance, the guess that didn't go over).
- **Season standings:** total points, then POWs won, wins, Monday night wins, Sunday night wins.
- **Awards and the Low Point Loser (LPL):** `packages/shared/src/awards.ts` works them out from a final week's results. The LPL is last place by the weekly ranking (shared if still level; nobody when the whole league is level). The others are perfect week, bullseye (exact tiebreaker total) and lone wolf (alone on the covering side of a game at least three players picked).
- **League events:** one notification kind, `league_event` (Settings → **Results and updates**, by email and per device; `profiles.email_league_events`, `push_subscriptions.league_events`; its own unsubscribe link), for results and updates in a league: being added through Start with members from today, and the type teams' events (week open/final in automatic leagues, numbers drawn, quarter results, pool won). Queue it with `queueLeagueEvent` inside the transaction that made the change, then `deliverLeagueEventsSoon` after commit; the dedupe key is per event and player (`league_event:<leagueId>:<userId>:<event>`, push event key `<leagueId>:<event>`), so a repeated run queues nothing twice. `pushOnly` skips email (squares quarter results, to spare the email budget). Payloads carry the league's name and the event, never a pick, a team, a square or whether the reader is in or out. Membership and the switch are rechecked just before sending.
- **Email:** Supabase Auth sends sign-in emails (sign-up confirmation, which production requires; password reset, email change, change notices) through Cloudflare Email Sending's SMTP relay. The Worker sends notification emails through its `send_email` binding: a new message thread (to the league's other current members), league events (above) and a pick reminder (7pm league time the evening before a game day, to members with games still to pick that day; it expires at the day's first kickoff). Notification emails are queued in `email_outbox` with a dedupe key and sent after the request commits, never inside it; addresses are read from `auth.users` at send time and never copied. Just before sending, a thread email is skipped if the recipient has left the league, and a reminder is skipped if it no longer applies (left, week not open, everything picked) or re-rendered with only the games still unpicked. Each kind can be turned off per player (`profiles.email_*`), and every email carries a signed unsubscribe link. Every send first reserves a slot in `email_usage` against `EMAIL_DAILY_LIMIT` / `EMAIL_MONTHLY_LIMIT` (a safety cap against runaway sending, defaults 1,000 a day and 10,000 a month); over budget, emails wait for the next UTC day. The count holds real sends only: when Cloudflare's own daily quota refuses a send, what's due waits for tomorrow and nothing is counted. Don't add a send path that skips the outbox. The Worker's Cron Trigger runs `runScheduledJobs` (automation, then email and push) every five minutes (`pnpm dev` uses a one-minute timer); the job must stay idempotent. In each job a failure to queue (caught per week) never stops sending what's waiting. Email is off until `UNSUBSCRIBE_SECRET` is set.
- **Push notifications:** opt-in per device in Settings → **On this device** (`push_subscriptions`). Your leagues suggests it once per browser (`NotificationsPrompt.web.tsx`: only while the browser hasn't asked for permission, or in an iPhone tab; **Not now** sets `pow:notifications-prompt-dismissed`). Keep it a suggestion, not a permanent row. New threads notify other current members who opted in; missing-pick reminders use the same 7pm rule as email (`dueReminderDay`) and expire at the day's first kickoff. Deliveries are queued in `push_deliveries` (inside the thread's transaction for new threads), and membership, preferences, week state and missing picks are rechecked just before sending. Payloads carry league names and thread titles, never picks or message bodies. Signing out disconnects the device. The website uses Web Push (`src/lib/notifications.web.ts`); the iPhone app uses Expo's push service (`src/lib/notifications.ts`, `EXPO_PUSH_ENABLED`), and both share the same queue and rules. When a browser replaces its subscription, the service worker reports the change and the app re-registers it for the same player (`oldEndpoint` on `PUT /push/device`). A device is removed only when its push service says the subscription is gone (404/410); other failures are logged by a fixed code and never remove it, since a 401/403 or an outage may be our side's fault. Push is off until the three `VAPID_*` secrets are set, and stays off if they don't form a matching pair.
- **Automation:** `advanceLeagues` (`src/automation/`) runs first in every cron run, failing on its own: for each type, the leagues its handler says have something due (a bounded batch), each advanced and caught on its own (`automation_due`, `automation_league`). The same `advanceLeague` runs on read through `advanceLeagueOnRead`, at most once a minute per league. Hands-on weekly leagues are never advanced. Steps must be idempotent, take their week or board row lock, and queue their notifications in the same transaction. An admin's game edit in a league that runs itself advances it at once (`advanceLeagueOnRead(…, { force: true })`), so a week opens as soon as its last line is typed in and finalizes as soon as its last score is. Weekly and playoff share `automation/pickem.ts` (`advanceDraft`: once the plan's opening time has come, refresh the slate from the feed, the whole slate only while the week has no games, so a game the admin removed stays removed, then open in the same step; `advanceOpen`: follow the feed's kickoffs for games still to finish (`followKickoffs` in `weekOps.ts`: never a spread, and points only until the week's first kickoff), fill finals, then finalize; `prepareWeek`), each step reading the feed before its transaction through `ctx.results` (once per NFL week per run) and locking the week row with `for update`. A week with no games is never "every line in" or "every result in". Every type's due query selects only leagues with something to do, in random order (`order by random()`), so leagues waiting on nothing can't hold the batch and a busy day (more due leagues than one batch) reaches everyone within a few runs. `AutomationContext.onlyLeagues` scopes a run to named leagues: the E2E harness and the API tests use it, production never does.
- **Start season:** `POST /leagues/:id/seasons` (admin) takes `{ year, settings?, startWeek? }` (`startWeek` is merged into the settings), parses them with the type's schema and dispatches, inside a transaction holding the league row lock, to the type's `startSeason` hook (`typeHooks.ts`; a type without one answers 409: squares, and hands-on weekly, which starts a season with its first week). A hook only writes rows and never calls the feed; the route advances the league right after commit.
- **Automatic weekly:** `automation/weekly.ts`. Start season stores `{ startWeek }` and creates the start week as an empty draft (refused for a season already over); the season automation runs is the league's latest with weeks, through Week 18, while it is this NFL season. **Draft and open happen together, on the week's Tuesday**: at `weeklyOpensAt` (the last Tuesday 9 AM Eastern at or before the first kickoff; `packages/shared/src/weekly.ts`) the next week is created (once every week is final; a week whose games have all kicked off is skipped), its slate and that morning's lines are imported, and it opens in the same run. Nothing is imported before then, an empty draft included (`PickemPlan.opensAt` gates the first import), so lines are never drawn days ahead; don't bring back a Monday-night draft. Spreads freeze at open (automation imports into drafts only, `importSlate(…, { keepAdminSpreads: true })`; points set by hand and an explicit tiebreaker are never touched). A draft that already has games (the admin imported it by hand, or a line was missing on Tuesday) keeps following the feed and opens once every game has a line. The due query waits accordingly: an empty draft is due from a week before its estimated start (`estimatedWeekStart`), and a final latest week once a Tuesday 9 AM has passed since it began. A line still missing 24 hours before the first kickoff (`missingLineDue`) is a league event to the admins only, once (`missing-line:<weekId>`). While open, kickoffs follow the feed (a rescheduled game locks at its new time) and results fill in (never over a typed score), then the week finalizes; league events `week-open:<weekId>` and `week-final:<weekId>:<finalizedAt>`. In a league that runs itself (`management` auto, playoff included) an admin's spread and point edits stop at the week's first kickoff (`slateEditable`), and a final week's score is corrected in place (`PATCH /games/:id` on a final week takes scores only, never clears one, and bumps `finalized_at` so the recap shows again); the app hides Reopen there and offers no announcement thread. Switching to Automatic picks the weeks up as they stand; switching back stops it. Weeks created by hand (Set up a week) stay the admin's override.
- **Playoff pick'em:** rules in `packages/shared/src/playoff.ts` (`roundPoints` 1/2/3/4 for weeks 19–22, `guillotineStatus`, `playoffStandings`, `wildCardPollingStarts`), routes in `apps/api/src/playoff.ts`, automation in `automation/playoff.ts`, reminders in `reminders/playoff.ts`, screens in `apps/mobile/src/screens/playoff/`. A round is created once the feed lists all its games with real teams (`PLAYOFF_ROUND_GAMES`; the Wild Card round only from Week 18's Sunday, `wildCardPollingStarts`; a round already played is skipped), opens as soon as every game has a line, finalizes once every game has a result, then the next is prepared; manual rounds come from `POST /leagues/:id/playoff/rounds` (the feed-failure fallback), and Auto-fill, Open and Finalize stay on `/weeks/:id/manage`. The format (`seasons.settings.format`, Start season) can't change after the first Wild Card kickoff; the POW bonus is `PLAYOFF_POW_BONUS` (Traditional 3, Guillotine 1), passed to `scoreWeek` through `roundPowBonus`. The Super Bowl round has no POW in either format (`roundHasPow`): the pick sheet hides it, the week view says `playoff.pow: false`, a save that names one is refused, and scoring ignores one saved before. Guillotine: a losing POW, or none once every game of the round has locked, puts a player out from the next round (a push survives; the round's picks still score; the Super Bowl puts nobody out); a late joiner is out by having no POW. `PUT /weeks/:id/picks` refuses an eliminated player any change but their guess. Status is never stored: a player's own (`WeekView.playoff.me`, from their own picks, as soon as a POW game ends); everyone's in `GET /leagues/:id/playoff/standings`, from final rounds only. Champion: points, wins, then the Super Bowl total guess (the `tiebreaker_guesses` row on week 22; on equal distance the guess that didn't go over), shared when still level; no round winner (`isWinner` false) or Low Point Loser; the week view's tiebreaker game is null before the Super Bowl. Reminders skip eliminated players, and on a Guillotine round's last game day a player who has picked every game but chosen no POW gets "Choose your POW" instead (`reminders/playoff.ts`; the same day's dedupe key, so one reminder either way). The pick sheet and manage screen say "round" where weekly says "week" (`weekUnit` in `lib/weekPresentation.ts`), and a player the guillotine put out sees no save bar except **Save guess** in the Super Bowl. `GET /leagues/:id/standings` is weekly pick'em's alone (404 here). League events round open/final; recap per round (round points, place, in or out; the champion after the Super Bowl). The header selector reads "2026 playoffs". Seed: `supabase/seeds/playoff.sql`.
- **Reminders by type:** `reminderTargets.ts` asks each type's `ReminderHandler` (`due`, `stillDue`) who is due; weekly's is today's rule (games still unpicked); playoff skips eliminated players, survivor reminds alive entrants with no pick, and squares reminds members holding no square on an undrawn board the evening before kickoff. A reminder's dedupe key names its week or board (`reminder:<weekOrBoardId>:<date>:<userId>`), and the send-time recheck finds the type from it. A `text` reminder's push title is its own heading ("Claim your squares", "Make your Week 5 pick", "Choose your POW"); only weekly's game list is titled "Make your picks". The 7pm rule (`dueReminderDay`) is shared.
- **Survivor:** rules in `packages/shared/src/survivor.ts` (`checkSurvivorPick`, `survivorStatus`, `usedTeams`, `survivorEntrants`), routes in `apps/api/src/survivor.ts`, automation in `src/automation/survivor.ts`, reminders in `src/reminders/survivor.ts`, screens in `apps/mobile/src/screens/survivor/` (Pick, Standings, the League tab's admin tools, the recap). Settings per season: lives 1–3 and the start week (any week with no kickoff yet by the calendar estimate `estimatedWeekStart` in `seasons.ts`, where the one Labor Day calculation lives (`openingThursday`); the next one by default), fixed once the start week's first game kicks off. `startSurvivorSeason` (league create, and `survivorHooks.startSeason`) stores them and creates the start week empty; it never calls the feed, so automation imports it on the next read or cron run. One pick per player per week (`survivor_picks`), straight up; no team twice in a season, the used teams reset at the Wild Card round, and on a playoff slate with no unused team left to play any team may be picked. A pick changes until its team's kickoff, and only to a team whose game hasn't kicked off. Saving (`PUT /weeks/:weekId/survivor-pick`; an admin may name `userId`, which sets `by_admin`) is one transaction holding the week row and the player's advisory lock. Reveal: another player's pick is returned by no route until its game has kicked off or has a result, not even that it exists; admins included. Status is never stored: a loss, a tie, or no pick in a final week is a strike; out when strikes reach the lives; a player not in the league at a week's last kickoff (`week_participants` once recorded) is out from that week; a week that would put out everyone still in puts out nobody and its strikes are cancelled; one left after a final week wins; several still in after Week 22 share the title. Who is in: everyone in the league at the start week's last kickoff who joined before it, plus anyone who picked in the start week; later joiners watch (`watching`). Every final week, the start week included, records who was in the league at its last kickoff (`recordSurvivorParticipants`, the same `weekParticipants` rule as other types), and status reads that record, never today's membership: a start-week picker missing from it is listed as out ("Left the league"), one who left without picking isn't listed, and rejoining later changes nothing. Don't derive who left from `joined_at`/`removed_at` once a week is recorded: a rejoin rewrites both. Automation: a week with no games is imported (a postseason week only once the feed lists the whole round, `POSTSEASON_GAME_COUNTS`) and opens at once; a week with games is never imported again, so a removed game stays removed; while open, kickoffs follow the feed and finals fill in, never over a typed score; when every game has a result (an empty slate never counts) the week finalizes, records its players, and queues one league event (`week-final:<weekId>`, or `pool-over:<seasonId>:<week>` when the pool ended), then the next week is created. Admin corrections, survivor-guarded: `DELETE /survivor-games/:gameId` (a cancelled game in an unfinished week; picks on it go; a week keeps one game) and `PATCH /survivor-games/:gameId` (scores at any time). Reminders go to alive entrants with no pick, on the 7pm rule.
- **Results recap:** the first time a player opens a league after a week is finalized, a bottom sheet (`WeekRecap` in `src/screens/weekly/WeeklyTabs.tsx`, the type's `Recap` in `LEAGUE_TYPE_SCREENS`) shows how they finished and the awards, once. `weeks.finalized_at` is set on finalize and cleared on reopen; `week_recap_views` records who has seen it, and a view older than `finalized_at` doesn't count, so a corrected week is recapped again. The league endpoint's `recapWeekId` names the latest such week closed since the player joined. The admin who finalizes is marked as having seen it. Weeks closed before the feature have no `finalized_at` and never get one.

## Design

Paths below are under `apps/mobile/src/`. The app draws with React Native primitives (`View`, `Text`, `Pressable`) and `StyleSheet`; react-native-web turns them into DOM and CSS on the web.

- **One theme, dark only.** Tokens live in `components/theme.ts` (`colors`, `fonts`): navy surfaces, electric blue (`primary`) for the player's pick and the main action, red (`pow`) for the Pick of the Week and nothing else, green (`win`) for won picks and results, coral (`destructive`) for lost picks, errors and removals, `colors.avatars` for player avatars, and `*Tint` fills. Use the tokens; don't hard-code colors.
- **Surfaces, not outlines.** Layers are told apart by fill: `background` → `card` → `raised` (selected rows, unpicked buttons, hover). Borders are hairlines for dividers, not boxes around cards. Corners are soft: controls 10px, team and POW buttons 12px, cards 16px, bottom sheets 22px, badges and pills fully round. No colored left-border stripes for callouts or highlights; use a tinted fill or an icon.
- **Type, two levels:** Barlow Condensed capitals (`fonts.display*`) for page and section titles, team names, scores and big stat numbers. Barlow, in sentence case, for everything else: buttons, badges, tabs, table headers, labels, small headings (`Eyebrow`) and card titles. Both are bundled as files in `apps/mobile/assets/fonts/` and loaded in `app/_layout.tsx`, so the app makes no third-party font requests. Text goes inside `Text` or one of the text components (Biome's `noReactNativeRawText`, configured in `biome.json`).
- **Copy:** say it once and briefly. Rules and footnotes go behind a disclosure (`Disclosure` in `screens/leagueUi.tsx`, or "How locks work" on the pick sheet) or on How to play (`app/how-to-play.tsx`), not in paragraphs above the content. Message times use `messageTime` (`lib/messagePresentation.ts`). Say "commissioner", never "admin", in anything players read (see "Admins (commissioners)"). Don't name the data provider (ESPN) in anything players or commissioners read: say "Auto-fill games and spreads", "Auto-fill results", "fill in automatically" or "the NFL schedule", so the provider can be swapped without changing the app's words. Code, logs and developer docs still name it.
- **Components:** the building blocks are in `components/ui.tsx` (`Screen`, `Card`, `Title`, `Body`, `Eyebrow`, `Button`, `Field`, `Notice`, `Badge`, `Sheet`) and, for league screens, `screens/leagueUi.tsx` (`Card`, `Heading`, `Label`, `Pill`, `Action`, `IconButton`, `RowLink`, `Input`, `Select`, `Sheet`, `StatTile`, `Failure`, `Skeleton`); reuse them rather than styling a new control. They are already tuned for touch (44px controls, 16px field text so iOS doesn't zoom). Icons are Phosphor through `Icon` (`components/Icon.tsx`): each glyph is imported from its own file, since Metro doesn't tree-shake, so add a new one to its `ICONS` map. `Avatar` (`components/Avatar.tsx`) shows a player's initials; it is decorative, so show the name beside it. A choice from a list uses `Select`, which is the browser's own `<select>` on the web (`WebSelect.web.tsx`) and a `Menu` on iPhone.
- **Phone first.** Tap targets are at least 44px. Use a whole-row link (`RowLink`) rather than a word of link text. The league tabs (`LeagueTabBar` in `screens/LeagueChrome.tsx`) are a bar along the bottom on phones and a row at the top from 768px wide; anything pinned to the bottom edge sits above the bar and the safe-area inset. Tables are rows of `View`s with explicit `role="row"`/cell roles so screen readers keep the table semantics; a table that scrolls sideways keeps its player column in place (`stickyFirst` in `screens/SeasonDashboard.tsx`) and marks the signed-in player's row.
- **Matchup sheet:** each pick card has a "Stats & news" row that opens `MatchupSheet` (`screens/MatchupSheet.tsx`, a bottom sheet) for that game, loaded on demand from `GET /api/games/:gameId/insights`. Everything in it is public background from ESPN (team form, injuries, leaders, news, and the Matchup Predictor's chance of each team winning outright), never this league's picks, so it doesn't touch the privacy rule. ESPN can fail or change without notice: each summary section is parsed on its own and a changed one drops out, and a failed lookup returns `matchup: null`. No sportsbook or prediction-market prices, branding or betting links.
- **Team badges** are the app's own drawings, never the teams' logos: `TeamLogo` (`components/TeamLogo.tsx`) draws a disc in the team's colors with a generic glyph for the team or its city (a cactus for Arizona, cheese for Green Bay), from `lib/teamBadges.ts`, keyed by the team abbreviation; anything else gets a plain football. Don't load or trace a team's real mark, and don't pick a glyph that is one (a star for Dallas, a horseshoe for Indianapolis). They are decorative: always show the team name or abbreviation beside one. The app loads no third-party images; the Content-Security-Policy in `apps/mobile/public/_headers` allows none, so any new external host must be added there.
- **Security headers.** `apps/mobile/public/_headers` sends HSTS (six months, `www` only), a CSP (scripts from `'self'` only; styles from `'self'` and `'unsafe-inline'`; images from `'self'` and `data:`; connections to `'self'` and Supabase), `frame-ancestors 'none'`, nosniff and a referrer policy with every page; the API adds the same through `secureHeaders()` plus `Cache-Control: no-store`. Keep inline scripts and inline `style` attributes out of `apps/mobile/public/index.html` (react-native-web and expo-font inject `<style>` elements at runtime, which `style-src 'unsafe-inline'` allows). `scripts/headers.test.mjs` checks all of this.
- **Installable.** `apps/mobile/public/manifest.json` and the `apple-*` tags in `apps/mobile/public/index.html` let the website be added to a phone's home screen, where it opens without browser chrome. The icons are committed PNGs drawn by `scripts/icons.mjs`. The only service worker is the push-only `apps/mobile/public/push-sw.js` (served `no-cache` via `_headers`); it caches no pages or responses, so nothing works offline (its one Cache Storage entry is the endpoint of a push subscription the browser replaced, for the app to report). Metro puts a content hash in everything under `/_expo/static` and `/assets`, which `_headers` caches as immutable. Keep the manifest's `theme_color` equal to the page's `theme-color` meta tag (`scripts/manifest.test.mjs` checks it).
- Ask with `showConfirm` (`lib/dialogs.tsx`) or `confirm(...)` in `screens/leagueUi.tsx`, never `window.confirm` or `Alert.alert`, so the question looks the same in the browser and on iPhone.
- **Secondary and destructive row actions** (member roles and removal, removing a game, pinning a thread) live in a "⋯" `Menu` (`components/Popover.tsx`, anchored with `useAnchor`) on the row, named `Options for <name>`; each `MenuItem` keeps a full accessible name ("Remove Pat"). Keep the one main action of a screen as a visible button.
- **Results are never color alone.** A won pick also gets a check, a lost one a strike-through, a push an equals sign, and each says "won", "lost" or "push" to screen readers (`screens/WeekResults.tsx`).
- **Loading:** show a placeholder shaped like the screen (`Skeleton` in `screens/leagueUi.tsx`, or the screen's own), never a bare "Loading…" line; each is named for what is loading and marked busy. The exception is opening the app: `Splash` (`components/Splash.tsx`), the POW mark over the whole screen, covers loading the fonts (`app/_layout.tsx`), then the session and profile (`screens/AuthScreen.tsx`), greeting the player by name once it's known. A load that fails shows `Failure` (`screens/leagueUi.tsx`) or `ErrorMessage` (`components/ui.tsx`) with **Try again**, never a dead end; a lost session signs the player out with "Your session ended" (`lib/api.ts`).
- **Feedback goes where the user is looking.** The outcome of an action is announced with `notifyDone` / `notifyError` (`lib/notify.tsx`), a banner (`NotificationBanner`) pinned near the bottom, above the tab bar and the save bar, never in a message at the top of a long page. The exceptions sit beside their button: the pick sheet's save bar, and validation inside a form (`Notice`). A button that starts a request is disabled and says what it is doing ("Saving…") until it finishes.
- **Unsaved work is guarded.** A screen with edits that haven't been saved calls `useEditsGuard` (`screens/leagueUi.tsx`) or `useFormGuard` (`lib/hooks.ts`), which register the work with `useUnsavedWork` and `useRemovalGuard` (`lib/unsaved.ts`). They ask before in-app navigation (the router's back, tabs, `go()`), the browser's back and forward buttons and the phone's back gesture (`lib/browserGuard.web.ts`), and the account menu's **Sign out**, and the browser warns on reload or tab close. Several parts of one screen can each hold a guard. Anything else that replaces the screen without the router seeing it awaits `confirmDiscard()` first.

## MCP servers (`.mcp.json`)

- `playwright` — drive a browser against the running app.
- `supabase` — the hosted Supabase project (signs in through the browser; run `/mcp` to authenticate). This is the **production** database: read freely, but schema changes still go through migrations, never ad-hoc SQL.
- Cloudflare: the `cloudflare` Claude Code plugin (marketplace `cloudflare/skills`) brings the Cloudflare MCP server and Workers skills. Use them, or `pnpm --filter @picks/api exec wrangler …`, for deploys, logs, secrets and Hyperdrive.
- GitHub needs no MCP server: use the `gh` CLI.

## Ports and worktrees

Every git worktree runs its own isolated stack, so agents can work in parallel.

- `scripts/ports.mjs` gives the main checkout (and CI) slot 0, the default ports: API 8787, Expo's Metro and web preview 8081 (`pnpm dev`, `pnpm mobile`), the local Worker 9787 (`pnpm worker:dev`, E2E), Supabase 54320–54329. Each linked worktree gets the next free slot `n`: API `8787+n`, Metro `8081+n`, Worker `9787+n`, Supabase `54320+10n` onward, and its own Supabase project (`football-weekly-picks-<n>`) with a separate database.
- Slots are recorded in `picks-port-slots.json` inside the shared `.git` directory and freed when the worktree directory is gone. Force one with `PICKS_PORT_SLOT=<n>`. CI selects an available port group with `scripts/ci-ports.mjs` before starting Supabase.
- `pnpm env:local` writes the API port into `.env` (`PORT`, with `APP_URL` on the web preview's origin); the API, `pnpm worker:dev` (`PORT + 1000`) and Playwright all read it from there. Run it after `pnpm db:start` in every new worktree.
- Before deleting a worktree, run `pnpm sb stop --no-backup` in it to remove its containers and database volume.
- The local stack runs only what the app uses: Postgres, Auth, the API gateway, Studio, and the test inbox (Mailpit). All local email, from Auth and from the API (under `pnpm dev` and `pnpm worker:dev`), lands in the test inbox; E2E tests read it through `e2e/tests/inbox.ts`. PostgREST (the Data API; `[api]`), Realtime, Storage, Edge Functions, and Analytics are switched off in `supabase/config.toml`; set `enabled = true` there when a feature needs one.

## Database changes

1. Edit `packages/db/src/schema.ts`.
2. `pnpm db:generate --name <short_description>` writes SQL to `supabase/migrations/` and refreshes the schema diagram in `docs/schema.md`. Review the SQL, including its order: drizzle-kit can write a composite foreign key before the unique constraint it refers to, which fails until the constraint is moved above it by hand.
3. `pnpm db:reset` rebuilds the local DB from migrations + seed.
4. Commit the schema change, the migration SQL, `supabase/migrations/meta/`, and `docs/schema.md`.

- For SQL Drizzle can't express (triggers, functions, grants): `pnpm db:migrate:custom --name <desc>`, then fill in the empty file.
- **Renames:** when a change could be either a rename or a drop + add, `drizzle-kit generate` asks interactively, and agents can't answer the prompt. Agents should not attempt a column or table rename on their own. Stop and ask the human to run `pnpm db:generate` in a terminal and pick "rename". (A hand-written custom migration doesn't help, because drizzle-kit diffs against its snapshot in `migrations/meta/`, not the live DB.)
- **Never edit a migration that has been merged to main.** Add a new one.
- Migrations deploy before the new code ships, so keep them backward-compatible (expand, then contract).
- CI fails if `schema.ts` changes without a matching migration, or if `docs/schema.md` is out of date.
- `docs/schema.md` (ER diagram + table reference) is generated by `packages/db/scripts/erd.mjs`; never edit it by hand. Its descriptions are the `/** ... */` comments above tables and columns in `schema.ts`, so document new tables and columns there. A comment-only change needs `pnpm db:erd`.

## Testing

| Layer    | Tool                                       | Location                                               | Covers                                                                    |
| -------- | ------------------------------------------ | ------------------------------------------------------ | ------------------------------------------------------------------------- |
| Unit     | Vitest (Node)                              | `packages/*/src/**/*.test.ts`                          | Pure logic and Zod schemas                                                |
| API      | Vitest + `app.request()`                   | `apps/api/test/`                                       | Routes, auth, DB behavior. DB suites skip unless `DATABASE_URL` is set    |
| App      | Vitest (Node)                              | `apps/mobile/src/**/*.test.ts`                         | The app's pure helpers and API/session adapters. No network               |
| E2E      | Playwright Test (Chromium + mobile WebKit) | `e2e/tests/`                                           | Real user flows across the Expo web build → Worker API → Supabase         |
| Script   | Node test runner                           | `scripts/*.test.mjs`, `packages/db/scripts/*.test.mjs` | Deploy and database tooling, credential redaction, CI ports, the manifest |
| Contract | Vitest (Node, live network)                | `apps/api/test/contract/*.contract.ts`                 | ESPN's real responses against the app's URLs, schemas, parsers            |

**Workflow for agents. Follow this before saying a change is done:**

1. `pnpm check` must pass.
2. If the change touches UI, routes, auth, or the schema: run `pnpm test:e2e` with `pnpm db:start` running.
3. For UI changes, also check visually: with `pnpm worker:dev` (or `pnpm dev`) running, use the Playwright MCP tools to open its URL from `pnpm ports`, step through the changed flow, and take a screenshot. For iPhone-only behavior, also run `pnpm mobile:export`, and check on a device or simulator when it matters.
4. Add or update tests at the lowest layer that can catch the bug. E2E covers critical user journeys only.
5. If the change touches how ESPN is read (`nfl.ts`, `insights.ts`, or `TEAM_ABBRS` in `packages/shared`): run `pnpm test:contract`, and extend `apps/api/test/contract/` to cover any new field or convention the app relies on. The app reads ESPN leniently so it stays up when a feed changes; the contract checks are what notice.
6. When a rule or a player-facing flow changes, update the places that describe it: the How to play page (`apps/mobile/app/how-to-play.tsx`), the README ("Walking through a week", "League rules"), "Domain rules" here, and the comments at the top of `supabase/seed.sql`. The Terms of use (`apps/mobile/app/terms.tsx`) describe the moderation rules, limits and account deletion too.
7. When what the app keeps about a player changes, update the Privacy policy (`apps/mobile/app/privacy.tsx`) and its date in the same change: a new column or table holding something about a player, a new provider or external host (also `_headers`), a new kind of email or notification, a retention period, or what account deletion clears. Keep the App Store privacy answers (`apps/mobile/README.md`) saying the same thing.

Conventions:

- Query by role, label, or text (`getByRole("button", { name: "Eagles" })`), never by CSS class. Add `aria-label`s so elements are reachable this way.
- Keep components presentational (data and callbacks in via props), and put logic worth testing in pure functions in `apps/mobile/src/lib/` with a Node test beside them. The screens in `src/screens/` do the fetching (`app/` routes only pick a screen), and `src/lib/auth.tsx` holds the session and profile.
- E2E tests sign up a fresh user per test (the `signedIn` fixture), so they never share state. Tests delete only rows they created; never truncate.
- A journey that needs the feed or time to move by itself (a week, round, board or pool that runs itself) is a `*.sim.spec.ts` file driving the dev harness through `e2e/tests/harness.ts` (`resetHarness`, `setClock`, `setFeedWeek`, `runJobs(request, [leagueId])`). Playwright starts the Worker with `DEV_HARNESS=1`, which replaces ESPN with the scripted feed (an unscripted week has no games) and shifts the Worker's clock; the `simulated` project runs these files one at a time after the parallel projects, since the clock and feed are shared by the whole Worker (`--project=simulated --no-deps` runs them alone). Reset the harness before and after each test, move the clock only forward of real time (play a future season), and reload the page after moving it. Pass `runJobs` the journey's own league ids (`leagueIdOf(page.url())`): automation advances only those, since the future clock would otherwise play the seeded leagues forward (finalizing their weeks, drawing their boards) until the next `pnpm db:reset`.
- Time-dependent logic takes a `now` parameter, so tests pass a fixed date rather than mocking timers. In the API, read time from the `now` dep; in the app, from `now()` in `apps/mobile/src/lib/clock.ts`, never `new Date()`. That keeps the local `CLOCK_OVERRIDE` (README, "Simulating a different date and time") working.

## Conventions

- A text column with a fixed set of values lists them once in `schema.ts` and gets a CHECK from the same list (`oneOf`); `text({ enum })` alone is only a TypeScript type. A second foreign key between the same two tables repeats the first one's `ON DELETE` rule, never `NO ACTION`: which of the two Postgres checks first isn't guaranteed.
- Every table gets `.enableRLS()` with no policies. The client roles (`anon`, `authenticated`) also hold no grants on `public`, now or by default for new tables; a function added to `public` needs its own `REVOKE ... FROM PUBLIC`. The API connects as a privileged role; RLS stops clients holding the public publishable key from touching tables directly via Supabase's REST API. Don't add RLS policies unless clients are meant to query Supabase directly.
- Request and response shapes live in `packages/shared` (Zod). Validate input with `zValidator`. Names and titles (display names, league names, thread titles) use `singleLine`: they reach email subjects and notification titles, where a line break could forge a header.
- Auth: clients sign in with Supabase and send `Authorization: Bearer <access_token>`. `requireAuth` verifies it and sets `c.var.user`.
- Keep routes chained on the Hono instance, otherwise `ApiType` loses its route types.

## Credentials and logs

- Remote database connections require verified TLS. `packages/db/src/connection.ts` is the shared policy for the Node API and `check-db-url.mjs`; the public Supabase CA is bundled and scoped to Supabase database hosts. In production the Worker connects through Hyperdrive, which verifies the database with `--sslmode verify-full` and the same CA; the health check still confirms the database leg is encrypted. Never disable certificate verification to work around a trust failure.
- API logs use route templates, generated request IDs, fixed readable messages, known error codes, and safe source locations. Never print raw errors, SQL parameters, request bodies/headers, or raw URLs. Extend the safe diagnostic vocabulary in `apps/api/src/logging.ts` when adding a new operation.
- CLI wrappers redact credentials before printing. `supabase-env.mjs` intentionally exports local credentials to `.env` or `GITHUB_ENV`; do not pipe it into public logs. It registers Actions masks before subsequent steps run.
- E2E allows only local database and auth services, and its browsers reach only loopback hosts (`launchOptions.proxy` in `e2e/playwright.config.ts`), so a link to the live site fails the test rather than creating a production account. As a backstop, production Auth's Before User Created hook (`public.hook_reject_test_signups`) refuses sign-ups on reserved test domains (`example.com`, `.test`, `.invalid`…). Traces and screenshots are disabled because they can capture credentials. Reports contain test outcomes and are retained for three days. Host/proxy access logs need their own URL privacy settings.

## Runtime (Cloudflare Workers)

- `src/worker.ts` builds the app once per isolate and opens a Hyperdrive connection per request (and per Cron Trigger run). Hyperdrive's query cache is off (it isn't cleared by writes, so access checks and reads after a save would go stale); keep it off. Routes keep using `deps.db`; a stand-in forwards it to the current request's connection (`AsyncLocalStorage`). Don't touch the database outside a request.
- Work that outlives the response (a new thread's emails and notifications) goes through the `background` dep, which the Worker hands to that request's `waitUntil` and finishes before closing its connection. A bare un-awaited promise is cancelled once the response is sent. `waitUntil` has a time limit, so the outbox claims rows in small batches; whatever is cut off is retried by the cron.
- In-memory caches (`cached` in `insights.ts`, the results throttle in `weeks.ts`) are per isolate and keep only settled values: a Worker request must not await a promise another request started. Don't share in-flight promises, sockets or streams across requests.
- Workers Paid ($5/month): 10 million API requests and 30 million CPU-ms a month included, unlimited Hyperdrive queries. Static asset requests are free. API requests use roughly 10–130 ms of CPU (waiting on I/O doesn't count); `limits.cpu_ms` in `wrangler.jsonc` caps each invocation at 2 s, so raise it before adding heavier work. Keep heavy computation out of hot routes; Workers Logs show CPU time per request. A Workers spend limit blocks `/api/*` (error 1103) and the cron at $10 of usage, so a request flood can take the app down. A zone rate limiting rule (dashboard only) blocks an IP for 10 s after 50 `/api/*` requests in 10 s, before the Worker runs; the busiest real player so far peaked at 20. It only covers the custom domain, so `wrangler.jsonc` keeps `workers_dev` and `preview_urls` off. Request bodies over 64 KB get a 413.
- `CLOCK_OVERRIDE` is Node-only. The Worker reads only `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` (account deletion's Auth admin call), `OPERATOR_USER_IDS`, `UNSUBSCRIBE_SECRET` and the three `VAPID_*` keys (secrets), `APP_URL`, `MODERATION_MODE` (`enforce` by default; `off` is the emergency switch) and `NODE_ENV` (`production` in `wrangler.jsonc`; `pnpm worker:dev` sets `development`, which drops the TLS requirement for local Postgres and lets `INBOX_URL` send email to the test inbox), and optionally `EMAIL_FROM`, `EMAIL_DAILY_LIMIT` and `EMAIL_MONTHLY_LIMIT`. `DEV_HARNESS=1` (E2E only, passed through by `pnpm worker:dev`) is refused unless `NODE_ENV=development`; it serves `/api/dev/*` outside the API.
- Email Sending to players is why the account is on Workers Paid (the free plan sends only to verified addresses).

## Deploy (GitHub Actions → Cloudflare)

- Workflow actions are pinned to full commit SHAs with the version in a trailing comment (a tag can be moved; a SHA can't); Dependabot updates both. The `main` ruleset requires `check` and `e2e` to pass before a merge.
- `ci.yml` runs on PRs. Job `check`: Gitleaks history scan with redacted output, lint, typecheck (including the Worker against its runtime types), migration drift check, unit + script tests, the app's tests and iOS JavaScript bundle, Expo web build + Worker bundle (`pnpm build`). Job `e2e`: local Supabase, DB-backed API tests, Playwright against the Worker (report uploaded as an artifact).
- `uptime.yml` checks `$APP_URL/api/health` every 15 minutes and opens one `uptime` issue per outage, closing it on recovery. Cloudflare Notifications cover Worker errors, DDoS and certificates; Dependabot (`.github/dependabot.yml`) opens update PRs. README, "Monitoring and recovery", has the runbook (rollback doesn't undo migrations; the Free Supabase plan keeps no backups).
- `contract.yml` runs `pnpm test:contract` daily (and on PRs touching the ESPN parsing). A failed scheduled run opens an issue labeled `feed-contract`, or comments on the open one; the next passing run closes it.
- `deploy.yml` runs on push to main: CI → connection-string check → `supabase db push` → `pnpm build` → `wrangler deploy` → `scripts/check-live.mjs` (polls `$APP_URL/api/health`). The Expo web build and API go live together, but open tabs keep the old web build and installed iPhone apps keep theirs, so the API must stay backward-compatible with both. No `EXPO_PUBLIC_API_URL` may be set for the web build: it calls its own origin. A failed live check doesn't undo the deploy; `wrangler rollback` does.
- `apps/api/wrangler.jsonc` defines the Worker `pow-pickem`: assets from `apps/mobile/dist-web` with SPA fallback, `run_worker_first` for `/api/*`, the `HYPERDRIVE` binding, the `EMAIL` (`send_email`) binding limited to `noreply@pow-pickem.com`, the `AI` (Workers AI) binding for screening (left out of `pnpm worker:dev`'s config unless `WORKER_DEV_SCREENING=1`), the Cron Trigger (`*/5 * * * *`), placement in `aws:us-east-1` (the Supabase region), logs and traces on. `apps/mobile/public/_headers` caches `/_expo/static/*` and `/assets/*` as immutable.
- Secrets (GitHub environment `production`): `SUPABASE_DB_URL` (session pooler URL for migrations; GitHub runners are IPv4-only), `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`; variable `APP_URL`. Worker secrets (`wrangler secret put`): `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` (account deletion), optional `OPERATOR_USER_IDS`, `UNSUBSCRIBE_SECRET` to turn email on, and `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` to turn push on (README, "Push notifications"). Email setup (Workers Paid, domain onboarding, Supabase SMTP and templates) is in the README under "Email".
- The web build needs no env vars (it fetches `/api/config` at runtime). Supabase Auth's Site URL and redirect URLs must point at the public URL, and the redirect URLs must include `/reset-password`, `/auth/callback` and `/account` (and the app's `pow-pickem://` links, `apps/mobile/README.md`).
- Only `wrangler.jsonc`, `src/worker.ts` and the deploy job are Cloudflare-specific; `src/index.ts` still runs the API on any Node host with `PORT` and `DATABASE_URL`.
